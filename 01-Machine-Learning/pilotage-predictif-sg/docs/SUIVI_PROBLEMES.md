# Suivi des problématiques techniques rencontrées

> Les colonnes de dates sont laissées à compléter (`JJ/MM/AAAA`) : le
> dépôt ne contient pas d'historique Git ni de journal daté permettant de
> les déduire de façon fiable. Le libellé et la description de la
> solution, eux, sont établis à partir du code et de la documentation du
> projet (commentaires de `modelisation_volumes.py`, `predict_volumes.py`,
> `modelisation_retard.py`, `modelisation_anomalies.py`, `README.md`,
> `AMELIORATION_MODELES.md`).

| Index | Date du problème | Problématique technique | Date de résolution | Description de la solution |
|---|---|---|---|---|
| 1 | à compléter | Prophet (Bloc 3A — prévision des volumes) plante systématiquement sur l'environnement Windows local : le binaire Stan précompilé est incompatible avec cet environnement (VC++ redistributable, recompilation cmdstan depuis les sources et exclusions antivirus testés sans succès) | à compléter | Repli automatique sur SARIMA/XGBoost dans `modelisation_volumes.py` dès que l'entraînement Prophet échoue, sans interrompre le pipeline (le SARIMA a ensuite été enrichi de régresseurs exogènes calendaires, faisant chuter le MAE test de 1019 à 667, soit −34.5%). Option complémentaire pour évaluer Prophet malgré tout : notebook autonome `colab_prophet/prevision_volumes_colab.ipynb` exécuté sur Google Colab (Linux), avec `integrer_resultats_colab.py` qui ne réintègre le résultat que s'il bat le modèle local |
| 2 | à compléter | Les prévisions de volumes (`predictions_volumes_j30`) étaient ancrées sur la date réelle d'exécution du script plutôt que sur le dernier jour réel des données de `features_journalier`, provoquant un écart de plusieurs semaines entre l'horizon affiché et les données disponibles (bug diagnostiqué avec l'utilisateur) | à compléter | `predict_volumes.py` recalcule désormais l'horizon J+1 à J+30 à partir de `derniere_date` (dernier jour réel de `features_journalier`) au lieu de la date système. Correctif défensif équivalent côté application : `_avec_dates_correctes()` dans `app/pages/surcharge.py` reconstruit la date à partir de `horizon_j` plutôt que d'utiliser la colonne `date` telle quelle |
| 3 | à compléter | Le modèle de classification du risque de retard (Bloc 3C) était exporté sans information sur l'appartenance de chaque ligne au split train/validation/test, ce qui mélangeait les trois jeux dans la matrice de confusion affichée sur la page Fiabilité de l'application | à compléter | Sauvegarde des dates de coupure `date_fin_train` / `date_fin_val` dans l'export du modèle (`modelisation_retard.py`), permettant à `predict_retard.py` d'étiqueter correctement chaque ligne via une colonne `split` dédiée |
| 4 | à compléter | Le calcul d'importance SHAP sur le modèle de détection d'anomalies (Bloc 3D) peut échouer selon l'environnement d'exécution | à compléter | Bloc `try/except` autour du calcul SHAP dans `modelisation_anomalies.py` : en cas d'échec, la feature la plus importante est renseignée à `"N/A"` et le pipeline continue sans interruption |
| 5 | à compléter | La sélection automatique du meilleur modèle sur le Bloc 3B (charge par ETP) ne compare que les modèles *optimisés* entre eux (Ridge, ElasticNet, XGBoost après recherche d'hyperparamètres) sans se rabattre sur la configuration fixe d'origine si celle-ci est meilleure — cas observé en pratique : le Ridge fixe (MAE 10.95) surpasse le XGBoost optimisé retenu en production (MAE 11.28) | Non résolu — limite identifiée | Documentée telle quelle dans `AMELIORATION_MODELES.md` (Bloc 3B) comme résultat d'expérimentation honnête plutôt que dissimulée ; piste retenue pour la suite : faire comparer systématiquement, dans `modelisation_charge_etp.py`, le modèle optimisé retenu à la configuration de référence avant sélection finale |
